# Слои и владельцы файлов состояния

## Контекст

Проект состоит из трёх независимых слоёв: Node-хуки (`hooks/install.js`, `uninstall.js`, `update.js`, `lifecycle.js`), Python-скрипты (`hooks/bootstrap.py`, `hooks/statusline.py`, `scripts/mcpbar.py`) и Swift UI (`Sources/*.swift`). Между слоями нет прямых импортов — обмен данными идёт только через JSON-файлы в `~/.claude/control-bar/`. Единственный межпроцессный вызов — Swift спавнит `mcpbar.py` как `Process` в `runBackend()` (`Sources/Backend.swift`, комментарий «the script writes mcp.json and the model re-reads it») и не парсит его stdout: скрипт пишет `mcp.json`, модель Swift перечитывает файл. Если это направление нарушить, слои начинают требовать друг у друга знания о внутреннем устройстве — ровно то, чего дизайн избегает.

## Правила

- Обмен между Node-хуками, Python и Swift — только через JSON-файлы в `~/.claude/control-bar/`. Прямых импортов между слоями нет и быть не должно.
- Единственный разрешённый межпроцессный вызов — Swift спавнит `mcpbar.py` как процесс и не читает его stdout как источник данных; результат — только через файл `mcp.json`.
- `scripts/mcpbar_codex.py`, `scripts/mcpbar_resets.py` и `scripts/mcpbar_usage.py` — не отдельные скрипты, а модули `mcpbar.py`: команды `codex-*`, `claude-reset-credit`, `codex-reset-credit` и `usage` приходят через `mcpbar.py`, общие помощники модуль берёт оттуда, а `ROOT` читает как `core.ROOT` в момент вызова. `mcpbar_usage` и `mcpbar_resets` импортируются лениво, только своими командами: остальным их разбор транскриптов, sqlite и сетевой код не нужны. `build.sh` копирует в `.app` все четыре файла; новый модуль рядом с `mcpbar.py` туда же добавляется, иначе DMG-канал упадёт на импорте.
- Python не читает чужой `.mcp.json` проекта (`mcpbar.py:393-395`) — это конфиг Claude Code, а не файл состояния control-bar.
- Swift не пишет `mcp.json`, `limits.json`, `codex/mcp.json` и `codex/limits.json` напрямую — эти файлы формирует только `mcpbar.py` (и `statusline.py` для `limits.json`). `SessionBoard` исключает текущую версию закрытой сессии без удаления hook-файла: unlink после проверки PID мог бы удалить конкурентное новое событие. SessionEnd-hook остаётся владельцем удаления state-файла. Swift пишет только два своих файла: `dismissed-sessions.json` для Remove from list и автоматического reap, атомарно до изменения board, и `usage/prices.json` — пользовательские цены и «Map to» окна Usage (`UsagePriceSettings.save`), которые Python только читает. Автоматическая очистка сохраняет все закрытые версии одним batch; ошибка оставляет строки и показывается в панели, повтор — через пять секунд.
- `limits.json` — файл с двумя писателями (`capture_limits` в `hooks/statusline.py` и команда `limits` в `scripts/mcpbar.py`) и `model-windows.json` — тоже с двумя (`hooks/statusline.py` и `scripts/mcpbar.py`; `hooks/update.js` его только читает); формат между писателями согласован намеренно, оба должны сохранять совместимость при правке.
- `uiconfig.json` правит только пользователь вручную — в кодовой базе писателя нет, только чтение в `SessionLabels.swift`. Не добавлять код, который пишет в этот файл.
- Хуки (Node, Python) хардкодят identity-значения (bundle id, exec, app name) намеренно, а не читают `identity.env` — после копирования хуков в целевой проект `identity.env` недоступен. Это гвардит CI (`ci.yml:62-95`), не забытая интеграция.
- Внутри Swift-слоя: `StatusController` — единственный владелец путей и жизненного цикла приложения. Его хранимое состояние и `init` живут в `main.swift` (extension не может объявлять хранимые свойства), поведение разложено по extension-файлам по темам: `AppLifecycle.swift` (единственный экземпляр, предшественники, самовыход), `HookSetup.swift` (установка хуков), `Backend.swift` (запуски `mcpbar.py` и переключатели), `StatePolling.swift` (тик 0.4 с: перечитывание файлов состояния, reap, перерисовка), `Notifications.swift`, `Pets.swift`, а также `Updates.swift`, `Actions.swift`, `IconRender.swift`, `PanelWindow.swift`, `SettingsWindow.swift`, `UsageWindow.swift` (окно Usage: открытие, клавиши, запуски `usage` и погашения сброса, когда что перечитывать) и `UsageData.swift` (снимок окна из живого состояния). Новый метод контроллера кладётся в файл своей темы, а не в `main.swift`. Модели (`MCPModel`, `Sessions`, `DesktopSessions`, `RunningProcesses`, `Changelog`, `HookInstall`) — чистые структуры/парсеры без побочных эффектов на файловую систему помимо своего файла.
- Решения, которые раньше жили в `StatusController` без тестов, вынесены в `Sources/Model` и проверяются модельной проверкой CI: `SessionBoard` (жизненный цикл сессий: перечитывание файлов, reap, звонок, «нужен ты», имена-двойники, главная сессия), `LimitsBoard` (какие лимиты показывают иконка и полоса), `Provider` (чем различаются агенты: имя, значок, папка состояния, файл настроек), `BackendCommand` (слова командной строки `mcpbar.py`), `IdleQuit` (когда приложению можно выйти самому), `GitBranches` (ветка из `.git/HEAD`), `StateFileLook` (mtime-гейт перед `codex/*.json`), `ReleaseVersion` (порядок версий), `HookInstall.nodeCandidates`/`shellAnswer` (где искать node), `Provider.stateFiles`/`statePath` (листинг и путь файлов сессий), `MCPChange.notifications` (тексты баннеров), а для окна Usage — `UsageLimitsModel` (строки лимитов, темп, риска, сбросы и их фразы), `UsageSummaryModel` (свёртка сводки, форматы, математика графика), `UsagePricesModel` (редактор цен и запись `usage/prices.json`) и `UsageWindowModel` (что окно помнит, его клавиши, сборка снимка из простых значений, правила времени), `ClaudeLimitsPoll` (один запрос лимитов Claude одновременно). Контроллер читает диск и исполняет то, что они вернули; новое правило такого рода кладётся туда же, а не в контроллер.
- Все запуски `mcpbar.py` идут через `spawnBackend()` в `Backend.swift`: он пишет в лог stderr и код выхода любого неуспешного запуска. Второго пути запуска с выводом в `/dev/null` не заводить. У каждого запуска есть дедлайн (`BackendCommand.deadline`) — вторая страховка поверх собственных таймаутов скрипта, поэтому он всегда выше их, а не ниже; по истечении процесс останавливается, строка уходит в `problems.log`, completion вызывается. stderr собирается в файл (`HookInstall.run`), а не читается из пайпа до EOF. Причину отказа переключателя панель берёт из кода выхода и stderr (`BackendCommand.refusal`), stdout по-прежнему не читается.
- Полные проверки идут по `backendQueue`, записи переключателей — по отдельной `switchQueue`, чтобы клик не ждал конца проверки. Проверки сливаются по агентам (`MCPRefreshPoll`): переключатель Claude перепроверяет только Claude, команда Codex перечитывает Codex сама; запись во время идущей проверки того же агента заказывает ему ещё одну. Параллельную вторую проверку отсекает сам скрипт неблокирующим замком (`refresh.lock`, у Codex — `codex/refresh.lock`).
- Все команды запускают bundled `mcpbar.py` (`BackendCommand.backend`): он той же версии, что и бинарь. Путь плагина из `paths.json` — запасной, только когда в бандле скрипта нет, и выбирается заново при каждом запуске: каталог плагина несёт версию в пути и исчезает при его обновлении. Окну Usage это правило нужно особенно: старый скрипт не знает слов `usage`, `claude-reset-credit` и `codex-reset-credit` и не пишет `account.json`, из-за чего окно молча осталось бы без тарифа, e-mail и сбросов. Все точки запуска опроса лимитов Codex проходят через `pollCodexLimits`: свой таймер 300 с, открытия и включение настройки с общим debounce 60 с и одним активным запросом (`CodexLimitsPoll`). Опрос Claude идёт через `pollClaudeLimits` с тем же правилом одного запроса (`ClaudeLimitsPoll`; запрос без ответа дольше 120 с считается потерянным). Кнопка обновления окна Usage вызывает оба опроса с `force`: это пропускает минуту debounce, но не запускает второй запрос рядом с идущим.
- Исключение из правила дедлайна одно — погашение сброса: `BackendCommand.deadline` возвращает для него `.infinity`, и снаружи его не останавливают никогда. Оборванный запрос оставил бы неизвестным, потрачен ли кредит; его ожидания ограничены в самом скрипте. У сканирования `usage` дедлайн 600 с: зависший скан иначе держал бы кнопку обновления окна Usage до перезапуска приложения.
- Погашение сброса (`claude-reset-credit`, `codex-reset-credit`) тратит кредит на настоящем аккаунте и необратимо. В Swift оно запускается из одного места — кнопки подтверждения в диалоге окна Usage (`UsageStore.redeemReset`); ни таймер, ни открытие окна, ни тест его не вызывают. Тесты Python проверяют его только против подставных серверов и подставного `codex`.
- Контракт `install.js` → Swift — код выхода, а не текст: 0 значит «хуки на месте» (записаны, уже актуальны или ими владеет плагин), 73 — хуки Claude на месте, а `~/.codex/hooks.json` не прочитан или не записан, любой другой — «не установлены», 75 — `settings.json` поменялся во время записи. `checkHooks()` в `HookSetup.swift` читает, как завершился процесс, показывает причину в панели и в Settings и повторяет попытку по таймеру. Код 73 (`HookInstall.codexNotWrittenExit`) — отдельный вердикт `.codexNotWritten`, а не «не установлены»: причина — первая строка вывода установщика — видна только в Settings, без блока в панели и без таймера повторов, потому что хуки Claude работают. Ошибка `settings.json` и код 75 старше него: 73 ставится только поверх чистого завершения. Путь установщика, который ничего не записал, не должен выходить с 0 — иначе Swift снова примет отсутствие хуков за успех, как раньше принимал за успех node, упавший ещё в dyld. То же для половины Codex: несостоявшаяся запись `~/.codex/hooks.json` не выходит с 0 ни в канале приложения, ни в канале плагина.
- Панель (`PanelView`, `PanelTabs`) читает только `PanelStore`, а тот — только снимок, собранный в `PanelData.swift` из `StatusController`. SwiftUI-вьюхи не обращаются к `MCPModel`, `Sessions` и файлам состояния напрямую: односторонний поток «файлы → StatusController → снимок → вьюха» и есть причина, по которой панель можно перерисовывать 2.5 раза в секунду, не боясь, что она сама что-то поменяет.
- Обратное направление — только через методы `PanelStore` (`setServer`, `setTool`, `openSession`, …), которые зовут `StatusController`. Вьюха не запускает `Process` и не пишет файлы.
- Окно Usage устроено так же: вьюхи (`UsageView*.swift`) читают только `UsageStore`, тот — снимок `UsageSnapshot`, собранный чистым сборщиком `UsageSnapshot(_:)` из `UsageInputs`. Лимиты в снимке — те же значения, что рисует панель (`limits`, `codexWindows`), поэтому окно и панель не расходятся в цифрах. Действия идут через методы `UsageStore`. Файлы окна (`usage/*.json`, `account.json`, `reset-credit-result.json`) перечитываются по mtime только пока окно на экране. Режим `CONTROL_BAR_RENDER_USAGE` (`UsageRender.swift`) рисует окно в PNG из каталога-фикстуры тем же сборщиком и теми же вьюхами, не создавая контроллер; его проверка — первый исполняемый оператор `main.swift`.

## Контракты файлов состояния

| Файл | Канонический писатель |
|---|---|
| `state.d/<id>.json` | `hooks/update.js`; `hooks/lifecycle.js` удаляет на SessionEnd. Swift только читает и исключает закрытые версии из board |
| `mcp.json` | `scripts/mcpbar.py` (refresh) |
| `limits.json` | `capture_limits` в `hooks/statusline.py` и команда `limits` в `scripts/mcpbar.py` (двойной писатель; совпадение записей держит тест `LimitsWriters` в `tests/test_statusline.py`, образец для Swift — `build/seam/limits.json`) |
| `codex/state.d/<session_id>.json` | `hooks/update.js --provider codex` и `hooks/lifecycle.js --provider codex` — та же форма, что у `state.d/`, плюс поля `provider` и `surface`. Отдельный каталог, а не общий: у Claude-контракта свои правила reap, и чужой файл в `state.d/` вычистили бы по ним. Swift не удаляет файл при reap: board запоминает mtime исключённой версии и перечитывает новое событие. `RunningProcesses` подтверждает владельца CLI по tty и времени старта; controller опрашивает в фоне не чаще двух секунд, unknown сохраняет PID-проверку |
| `codex/mcp.json` | `scripts/mcpbar.py` (команда `codex-mcp refresh`) — единственный писатель; данные берёт у самого Codex (`codex mcp list --json`, `codex mcp get --json`, `mcpServerStatus/list` через `codex app-server`), а не из его `config.toml`: в системном python 3.9 нет `tomllib`, и разбирать чужой TOML со слоями руками — та же ошибка, которой скрипт избегает для `settings.json`. Форма файла совпадает с `mcp.json`, чтобы `MCPModel` читал оба одним парсером |
| `history.json` | `mcpbar.py claude-history` атомарно сохраняет до 50 последних разговоров Claude Code при открытии истории или по Refresh. Индекса у Claude Code нет, поэтому скрипт читает по 64 КБ с обоих концов самых свежих транскриптов верхнего уровня `~/.claude/projects/-*/<uuid>.jsonl` (если ни в одном окне нет сообщения, ищет первое сообщение дальше, до 16 МБ); SDK-сессии и подагенты пропускаются, копия сессии в другой папке даёт одну строку, текст сообщений в снимок не попадает. Нечитаемая `projects/` — ошибка, прежний снимок остаётся. Панель исключает сессии, которые уже видны в Live. |
| `codex/history.json` | `mcpbar.py codex-history` атомарно сохраняет страницу метаданных из `thread/list` при открытии истории или по Refresh. Запрос использует локальный индекс Codex с фильтром аккаунта. Панель читает снимок после успешной записи и исключает сессии, которые уже видны в Live. |
| `~/.codex/config.toml` | **не наш файл**: переключатели серверов и инструментов Codex пишет сам Codex через `config/batchWrite` у `codex app-server` (`codex_config_write` в `mcpbar_codex.py`). Своего TOML-писателя не заводить — комментарии, форматирование и чужие таблицы должен сохранять владелец файла |
| `~/.codex/hooks.json` | `hooks/install.js` (мерж, чужие хуки не трогает) и `hooks/uninstall.js` (снятие только при полном удалении, не при `--hooks-only`). Доверие к хукам (`[hooks.state]` в `config.toml`) выдаётся только нажатием пользователя — в самом Codex или кнопкой приложения (`mcpbar.py codex-hooks approve`), никогда при запуске. Пишет его сам Codex через `config/batchWrite`, хеш берётся из его `hooks/list`: свой хеш не считать, чужие хуки не одобрять |
| `codex/limits.json` | `scripts/mcpbar.py` (команда `codex-limits`) — единственный писатель; сначала спрашивает `account/rateLimits/read` через read-only `codex app-server`. Полный успешный ответ заменяет все пулы, отсутствующий резерв удаляется. При ошибке читает последнее пригодное измерение из `~/.codex/sessions/**/rollout-*.jsonl`, сохраняя возраст каждого пула и более свежий кэш. `source` — `app-server` или `rollout`; наружу идут факты: пул, проценты, длительность окна, момент сброса, момент замера |
| `codex/limits-status.json` | `scripts/mcpbar.py` (`codex-limits`) — пишет `{ts,state,detail}` после каждого опроса, даже когда цифры не изменились. В `detail` только безопасная категория ошибки. Swift читает отдельное состояние Codex и показывает его независимо от Claude |
| `account.json` | команда `limits` в `scripts/mcpbar.py`, тем же единственным запросом, что и `limits.json` (`/api/oauth/usage?cedar_ember=1`): тариф из записи Keychain, e-mail из `~/.claude.json`, окна моделей кроме Fable (`extraWindows`), месячный расход (`spend`), накопленные сбросы с id грантов (`resetCredits`). Пишется только при состоянии опроса `ok`; неизвестное значение — отсутствие ключа, не `null`. `statusline.py` этот файл не пишет |
| `codex/account.json` | `scripts/mcpbar.py` (`codex-limits`): тариф, строка `individual`, число и ближайший срок сбросов из ответа `account/rateLimits/read`; e-mail из `account/read` не чаще раза в 24 часа (служебный ключ `emailCheckedAt`). Обновляется при любом ответе app-server (состояния `ok` и `empty`) и не трогается на запасном пути через rollout |
| `reset-credit-pending.json`, `reset-credit-result.json`, `reset-credit.lock` и те же три под `codex/` | `scripts/mcpbar_resets.py` (команды `claude-reset-credit <creditId>` и `codex-reset-credit`). Файл исхода пишется при каждом запуске, кроме запуска, который ничего не отправил, пока прежняя заявка открыта (её запись с `requestFailed` или `unconfirmed` и её ключ остаются): `{ts, provider, creditId, outcome, error, confirmed}`, в `error` только фиксированная категория (у Claude среди них `cliUnavailable`: `claude --version` не назвал версию, заявка не уходила; категорию без своей фразы Swift показывает общей). Swift читает исход из файла, а не из кода выхода; ключ идемпотентности в pending живёт до определённого ответа сервиса |
| `usage/summary.json`, `usage/status.json` | `scripts/mcpbar_usage.py` (команда `usage [--refresh]`) — единственный писатель. Сводка — четыре периода (`"1"`, `"7"`, `"30"`, `"90"`) с корзинами и по одному источнику на провайдера; стоимость, алиасы и свои цены применяет Python, Swift стоимость не пересчитывает. `status.json` — прогресс в файлах во время `scanning` и итог; «идёт ли сканирование» Swift знает по своему флагу, а не по файлу. `message` источника и `detail` статуса — фиксированные категории, предложения из них делает Swift |
| `usage/prices.json` | **Swift** (`UsagePriceSettings.save`, окно Usage) — единственный писатель; Python только читает и строго проверяет, негодную запись молча пропускает. Пустую кэш-цену Swift не пишет вовсе: явный `null` делает запись негодной |
| `usage/scan-cache.sqlite3`, `usage/model-rates.json`, `usage/rates-state.json`, `usage/scan.lock` | служебные файлы команды `usage`: разобранные записи транскриптов (без текста сообщений), таблица цен LiteLLM и время её загрузки, замок одного сканирования. Swift их не читает |
| `dismissed-sessions.json` | Swift `SessionDismissals`: `{ "<provider>:<id>": "<fingerprint>" }`. SHA-256 от canonical state JSON и точного mtime; `SessionBoard.dismiss` и `tick(persistReaped:)` сохраняют marker до снятия строки и перепроверяют версию после записи; исключение переживает рестарт и повторное использование PID. Новое событие возвращает строку. Ошибки видны через `PanelStore`, история и процессы не изменяются |

## Примеры

НЕПРАВИЛЬНО: Swift напрямую пишет запись в `mcp.json` после получения данных о сервере — теперь у файла два независимых писателя с несогласованным форматом, и `mcpbar.py` может затереть изменения Swift при следующем запуске.
ПРАВИЛЬНО: Swift спавнит `mcpbar.py` (`runBackend()` в `Backend.swift`) и ждёт, пока тот перезапишет `mcp.json`, затем перечитывает файл — единственный писатель, формат не расходится.

НЕПРАВИЛЬНО: `mcpbar.py` читает `.mcp.json` проекта, чтобы получить список серверов в обход штатного пути.
ПРАВИЛЬНО: `mcpbar.py` не трогает `.mcp.json` проекта (`mcpbar.py:393-395`) — это конфиг Claude Code, а не файл состояния control-bar; данные о серверах идут через собственный `mcp.json` слоя.
